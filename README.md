# Business Story Simulator

[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)
[![Version](https://img.shields.io/badge/version-2.0-blue.svg)](SKILL.md)

> 在写第一行代码之前，先把业务讲清楚。

一个面向 AI 编码助手（Claude Code、Qoder、Cursor 等）的开发前规划 Skill：把「我有个想法」推进到「有一份可以交给 AI 或开发团队执行的计划」。

它不写代码，只负责理解需求、模拟真实业务场景、检查业务闭环、确认规则，最后产出可执行的需求基线与开发工单。

## 解决什么问题

大多数返工不是因为代码写得不好，而是因为一开始就没说清楚：谁在用、什么时候触发、失败了怎么办、什么情况算完成。AI 编码助手会把这些空白自动补全成一个看似合理但并非你本意的系统。

这个 Skill 的作用就是在动手之前，把这些空白显式地问出来。

## 核心特性

- **两种用户模式**：小白模式（不会编码，靠 AI 做小项目）与开发者模式（懂技术，需要梳理业务与计划）。用户模式与分析深度是两个独立维度，不会混为一谈。
- **三档分析深度**：轻量（CRUD、小工具）/ 标准（中型业务应用）/ 深度（多角色、多模块、跨系统）。
- **七层分析**：项目全局、角色职责、模块关系、真实业务故事、状态与时间推演、异常与边界、需求与开发规划。
- **三次确认关卡**：方向确认 → 业务确认 → 计划确认。未确认的规则只能出草案，不会被伪装成定稿。
- **反向业务推演**：从结果倒推前置条件和中间环节，专门用来发现断链（该生成的记录没生成、该通知的下游没通知、错过的定时任务没人补）。
- **业务规则追溯**：每条重要规则记录来源（口述 / 文档 / 原型 / 数据库 / 代码 / 确认 / AI 建议）与确认状态，冲突并列展示，不擅自选边。
- **不写代码**：Skill 的职责到「计划可执行、规则可追溯」为止，不会替你做技术选型定案，更不会直接开始实现。

## 安装

Skill 的本质是一个带 `SKILL.md` 的文件夹，放到 Agent 的技能目录即可。不同工具目录不同，常见位置：

| 工具 | 用户级技能目录 |
| --- | --- |
| Claude Code | `~/.claude/skills/` |
| Qoder | `~/.qoder/skills/`（Windows：`%USERPROFILE%\.qoder-cn\skills\`） |
| 其他 Agent | 参考各自文档中的 Skill / 规则目录 |

直接克隆进技能目录（仓库根目录就是 Skill 根目录）：

```bash
cd ~/.claude/skills          # 换成你所用工具的技能目录
git clone https://github.com/zlc0099/business-story-simulator.git
```

或者手动下载本仓库，把整个文件夹复制进技能目录，确保入口文件名为 `SKILL.md`。

## 使用

在任务开始时明确要求使用该 Skill，例如：

```text
用 business-story-simulator 帮我梳理这个需求：我想做一个……
```

也可以通过斜杠命令触发（如果你的工具支持）：

```text
/business-story-simulator 我想给公司做一个设备巡检系统
```

### 小白模式

```text
用户：我想做一个记账工具，给自己用。
Agent：先确认一件事——这个账单最想替你解决什么麻烦？
       (1) 记不清钱花哪了  (2) 经常忘记按时交费  (3) 要给客户开账单
```

Agent 会负责技术判断，你只需要回答「你希望怎么用」「操作后希望发生什么」。

### 开发者模式

```text
用户：这是我们的工单系统代码和一份 PRD，想加一个 SLA 超时升级模块。
Agent：先做复杂度评估 → 建议深度分析 → 读取现有模块与边界 →
       按七层分析产出业务故事、状态流转、异常矩阵 →
       三次确认 → 生成需求基线与开发工单
```

## 工作流

```text
小白模式
想法收集 → 引导提问 → 典型场景 → 功能建议 → 首版范围
        → 故事模拟 → 页面/操作梳理 → 规则确认
        → 技术建议 → 验收清单 → 开发计划

开发者模式
读取资料 → 复杂度评估 → 七层分析 → 反向推演
        → 规则追溯 → 三次确认 → 需求基线 → 开发工单
```

## 适用场景

- 从零开始的新项目，只有口头想法，没有正式文档。
- 已有系统的新模块、流程改造、需求变更。
- 已经有 PRD / 原型 / 表结构，但需要核对并补齐业务闭环。
- 想把「大概这样」变成可以验收、可以交给别人执行的计划。

## 明确不做的事

- 不写业务代码，不做数据库设计定稿，不部署。
- 不替用户确认关键业务规则（涉及钱款、权限、删除、自动派发、外部通知等高影响行为时尤其如此）。
- 不把假设写成需求，不声称读取了没读过的文件、验证了没验证的行为。

## 兼容性

不绑定 IDE、模型、编程语言或项目管理工具。只要能加载 `SKILL.md` 作为指令的 Agent 都可以使用；即使工具不支持 Skill 机制，也可以直接把 `SKILL.md` 作为提示词引用。
